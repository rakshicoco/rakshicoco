Build 22 identified repeated sequential auth calls as the
dominant server-side latency source.

DO NOT perform infrastructure migration.

DO NOT disable RLS.

user ID.

============================================================
PHASE 2 — REQUEST-SCOPED AUTH
============================================================

Implement a request-scoped authentication strategy.

Goal:

ONE verified authentication resolution per request where possible.

Reuse the authenticated identity inside the same server request.

Do NOT call getUser() independently from:

middleware
layout
page
server action

when the same request has already established identity.

Use a safe server-side mechanism such as:

request-scoped cache/memoization

or another framework-compatible server request context.

The identity must remain derived from the authenticated session.

============================================================
CRITICAL SECURITY RULE
============================================================

NEVER trust:

x-user-id

or any arbitrary client-provided identity header.

If middleware forwards identity metadata internally:

1. Authenticate the request first.
2. Overwrite any incoming identity header.
3. Never use an incoming client value directly.
4. Authorization must still use verified authentication.
5. RLS must remain enabled.
6. Role checks must remain server-side.

Test explicitly:

Request A authenticated as User A.

Attempt to send:

x-user-id: User B

Expected:

Request remains User A.

Never allow User A to become User B through headers.

============================================================
PHASE 3 — SUPABASE CLIENT REVIEW
============================================================

Inspect createServerClient/createClient implementation.

Do not accidentally create multiple Supabase clients per request.

Ensure:

middleware client
server component client
server action client

are used appropriately.

Do not switch blindly from getUser() to getSession() simply for speed.

Server-side authorization must remain secure.

If getSession() is used for optimization anywhere,
verify that authorization is still cryptographically/session
validated and that Supabase's recommended server-side security
model is preserved.
