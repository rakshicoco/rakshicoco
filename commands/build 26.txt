BUILD 24 — PRE-IMPLEMENTATION CORRECTIONS

The Build 24 implementation plan is approved conceptually, but
the following corrections are mandatory before implementation.

============================================================
1. EXISTING REPOSITORY IS THE ROUTE AUTHORITY
============================================================

Do NOT blindly create every route listed in the plan.

First inspect:

src/app/
src/components/navigation/
src/lib/actions/
supabase/migrations/

Build an actual route registry:

ROUTE
CURRENT HREFS
EXISTING PAGE
EXISTING SERVER ACTION
DATABASE TABLE
STATUS

Classify every broken navigation target as:

MISSING_ROUTE
WRONG_HREF
MISSING_PAGE
MISSING_ACTION
DATABASE_ERROR
AUTH_ERROR

Fix the actual cause.

Do not create duplicate business workflows.

In particular inspect whether these already exist under
finance/sales/operations:

farm payments
labour payments
sales orders
sales detail
dispatch
bills
invoices

Only create a new route when there is no existing equivalent.

============================================================
2. RECYCLE BIN — DEPENDENCY SAFE
============================================================

Do NOT treat every entity as freely deletable.

Classify entities:

MASTER:
farms
buyers
teams
workers

OPERATIONAL:
purchases
cutting_batches
grouping_batches
transport_trips
processing_batches
dispatches
stock-related records

FINANCIAL:
bills
payments
expenses
sales orders with financial references

Rules:

MASTER records:
soft delete allowed.

OPERATIONAL records:
soft delete only if no downstream dependency exists.

FINANCIAL records:
never physically delete if they have financial,
payment, invoice, accounting, or audit dependencies.

Use:

TRASH
ARCHIVED
VOIDED
CANCELLED

appropriately.

Never destroy historical business traceability.

============================================================
3. 90-DAY DELETE
============================================================

After 90 days:

IF record has zero dependencies:
    permanent deletion may occur.

IF record has dependencies:
    retain record
    convert to ARCHIVED/VOIDED where appropriate
    retain audit history.

Never cascade-delete business history merely to satisfy
the 90-day cleanup.

Before every permanent deletion perform dependency checks.

============================================================
4. CLEANUP ENDPOINT SECURITY
============================================================

Do not create a publicly callable cleanup endpoint.

If using:

/api/cron/cleanup-trash

require a strong server-side cron authorization mechanism.

Never accept:

entity_id
user_id
delete confirmation

from an unauthenticated request.

Prefer the platform's scheduled-job mechanism.

Cleanup must execute only server-side.

============================================================
5. AVATAR STORAGE
============================================================

Do NOT make the avatars bucket public by default.

Prefer:

private bucket:
avatars

Store:

avatar_path

in profiles.

Generate signed URLs when displaying avatars.

Users may upload/update their own avatar only.

Do not permit role modification through profile editing.

============================================================
6. AI CONFIRMATION — SERVER ENFORCED
============================================================

AI must NOT execute a destructive/material mutation simply
because the LLM says that the user confirmed it.

Architecture:

USER REQUEST
    ↓
AI ANALYSIS
    ↓
PROPOSED ACTION
    ↓
SERVER CREATES PENDING ACTION
    ↓
UI SHOWS CONFIRMATION
    ↓
USER CLICKS CONFIRM
    ↓
SERVER VALIDATES AUTHENTICATED USER
    ↓
SERVER VALIDATES PENDING ACTION
    ↓
SERVER EXECUTES TOOL
    ↓
AUDIT LOG

The confirmation must be application state,
not prompt text.

Never trust:

"the user said yes"

inside an LLM response.

============================================================
7. AI TOOL SECURITY
============================================================

AI may NEVER execute arbitrary SQL.

AI may NEVER receive:

SUPABASE_SERVICE_ROLE_KEY
OPENROUTER_API_KEY

AI tools must use predefined server-side functions.

Every mutation must:

authenticate
authorize
validate with Zod
execute business logic
write audit event
return result

AI tools must reuse existing server actions/business services
where practical rather than duplicating business logic.

============================================================
